Android WASM 实验

把 Rembg Studio 的浏览器版（onnxruntime-web + u2netp）放到 Android 模拟器里跑通，并量化它。不引入 Appium，不 npm install。

9.5 s单图冷启动到出图
37.1 s10 张批次总耗时（≈3.7 s/张）
119 MBChrome 峰值 PSS

怎么做到

API 36 google_apis_playstore x86_64 镜像自带 Chrome 133。网页侧全部走 Chrome DevTools Protocol：adb forward tcp:9222 localabstract:chrome_devtools_remote，Node 24 自带 WebSocket，因此一个零依赖客户端脚本就能注入图片、点按钮、读 DOM。

没有声称的部分

这些是 x86_64 模拟器 + 软件 GL 的数字，不能当作 ARM 手机的性能证据； 原生端（Kotlin + ONNX Runtime）在同一台 AVD 上的对照脚本已经写好，但选图那一步尚未跑通， 因此这里不给出任何原生端数字。

踩过的坑

  1. 新镜像的 Chrome 首启引导会吞掉第一个 VIEW intent，且有两层（登录、通知）。
  2. 网页内容对 uiautomator 不可见；预览图是无 id 的 blob: 图，只能靠 alpha 通道认出抠图结果。
  3. 手写 SIMD 探测字节会误判：本项目真实产物 validate 为真，而猜出来的字节数组报假。
  4. 把大段 base64 拼进 Runtime.evaluate 表达式会静默失效，必须用 Runtime.callFunctionOn 传参。
  5. DOM.setFileInputFiles 给 /sdcard 路径必失败：scoped storage 拒绝 Chrome 读取，而 Play 镜像不能 adb root。
  6. #files 是 multiple，PhotoPicker 选完还要再点 Done。
  7. uiautomator 的 bounds 形状是 [x1,y1][x2,y2]；写成逗号分隔会表现为"按钮找不到"。
  8. 经 adb shell 回传的中文 text 不可靠，应改用 resource-id 与 ASCII 数字定位。
  9. 工作台会持久化批次队列，不清站点存储就会把上一轮结果当成本轮耗时。

关于线程

GitHub Pages 不发 COOP/COEP，所以没有 SharedArrayBuffer；这里没问题，因为 web/worker.mjs 把 ort.env.wasm.numThreads 钉在 1。将来若开启多线程， 线上 PWA 会先坏，而不是这个实验。
